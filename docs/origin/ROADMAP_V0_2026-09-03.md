## 0. Qué es ISyCoLang

ISyCoLang no nace como un lenguaje con un conjunto fijo de instrucciones. Nace como un **sustrato mínimo de tres slots operacionales reemplazables**.

El lenguaje fija la estructura mínima de ejecución, pero **no fija qué operación concreta ocupa cada slot**.

```text
ISyCoLang Core

STATE
MEMORY
DISPATCH
COMPOSE

Ω0
Ω1
Ω2
```

Cada pack instala una terna distinta:

```text
PACK_X
Ω0 = op_A
Ω1 = op_B
Ω2 = op_C
```

La terna no se elige por gusto. **Compite.**

El objetivo experimental es descubrir, para un dominio dado, qué base de tres operaciones maximiza capacidad útil bajo un contrato explícito de atomicidad y costo.

---

## 1. Hipótesis central

> Bajo un core fijo y una definición estricta de operación atómica, diferentes dominios pueden converger a distintas bases de tres operaciones con alta clausura composicional.

No se afirma que **3** sea la cota mínima universal de computación.

```text
CARDINALITY = FIXED_AT_3
UNIVERSAL_MINIMUM = NOT_CLAIMED
```

La pregunta inicial es:

> **¿Cuál es la mejor base de tres para este dominio bajo nuestras reglas?**

Después, si una base sobrevive, se podrá investigar si alguno de sus elementos es derivable y si la cardinalidad puede reducirse a 2 o 1 sin esconder una VM completa dentro de una sola operación.

## 3. Contrato mínimo del core

Versión conceptual inicial:

```text
Program  := sequence of instructions
Instr    := Ωi operands
Ωi       := one of exactly three loaded operations
State    := explicit machine state
Memory   := explicit bounded/unbounded model chosen by experiment
Step     := Ωi(State, operands) -> State'
```

El core no debe conocer semántica concreta de `Ω0`, `Ω1`, `Ω2`.

Debe conocer únicamente:

- cómo invocar una op;
- cómo registrar su transición;
- cómo avanzar control;
- cómo detenerse;
- cómo producir trace;
- cómo aplicar límites.

---

## 4. Operation Module Contract

Toda op candidata debe declarar como mínimo:

```text
name
version
input_arity
reads
writes
state_effect
memory_effect
control_effect
deterministic?
cost_model
preconditions
postconditions
```

Firma conceptual:

```text
OP(state, operands) -> new_state
```

No obligar a que una op sea "aritmética", otra "memoria" y otra "control". Eso metería la respuesta dentro del experimento.

---

## 5. Atomicity firewall

Sin esta regla el experimento se vuelve una trampa.

Prohibido considerar como op atómica algo equivalente a:

```text
EXECUTE_ARBITRARY_PYTHON
RUN_VM
EVAL_PROGRAM
DO_EVERYTHING
```

Regla inicial:

> **Una operación debe representar una transición local con costo observable y no puede ocultar un bucle, intérprete, VM o programa arbitrario no contabilizado.**

Cada op debe tener un costo explícito y auditable.

```text
POWERFUL_OP != FREE_OP
ONE_OP_CONTAINS_VM = INVALID_BASIS
```

## 6. Arena de 3 operaciones

Nombre temporal del laboratorio: **3OPS Arena**.

Entrada:

- catálogo de ops candidatas;
- dominio;
- corpus de tareas;
- límites de síntesis;
- engine(s) disponibles.

Proceso:

```text
candidate ops
    ↓
enumerate 3-op packs
    ↓
synthesize programs
    ↓
execute
    ↓
verify behavior
    ↓
measure cost
    ↓
rank / Pareto frontier
```

Si hay `N` ops candidatas, probar las ternas no es el problema principal:

```text
packs = C(N, 3)
```

El problema real es **sintetizar programas y medir qué puede construir cada terna**.

## 9. TRACE_MATH como capa de composición

TRACE_MATH no prueba por magia que un programa sea correcto.

```text
TRACE_MATH DOES NOT PROVE THE PROGRAM.
TRACE_MATH COMPOSES WHAT THE TRACE ALREADY PROVED.
```

Pipeline:

```text
Ω0 / Ω1 / Ω2
    ↓
execution traces
    ↓
TRACE_MATH normalization
    ↓
composable structural objects
    ↓
derived behaviors
```

Objetivos:

- detectar operaciones derivables;
- comparar una op directa contra una composición;
- reutilizar comportamientos ya verificados;
- reducir redundancia;
- construir biblioteca de macros/ops derivadas sin aumentar el número de primitivas.

Ejemplo conceptual:

```text
TRACE(Ω7)
≈
TRACE(Ω2 + Ω3 + Ω2)
```

Si la equivalencia sólo está observada en el corpus:

```text
DERIVABLE_IN_OBSERVED_DOMAIN = YES
GENERAL_EQUIVALENCE = NOT_DEMONSTRATED
```

## 10. 1+2=3 y 3-2=1

ISyCoLang debe soportar ambas direcciones del método.

### Composición

```text
1 + 2 = 3 :p
```

Unidades verificadas pueden componerse para formar una nueva unidad reutilizable.

### Reducción

```text
3 - 2 = 1 :p
```

Si varias ops/comportamientos contienen estructura redundante, reducirlos a una unidad canónica siempre que la evidencia relevante se preserve.

Regla:

```text
REDUCTION_PRESERVES_EVIDENCE = REQUIRED
COMPOSITION_INVENTS_BEHAVIOR = FORBIDDEN
```

```text

```


```text
ISyCoLang program
      ↓

      ↓
engine race
      ↓

      ↓

```

Regla:

> No elegir engine por reputación. Elegir por comportamiento medido en el workload.

```text
ENGINE_IDENTITY != ENGINE_FIT
```

## 12. WISA como primer dominio

WISA es un candidato natural para el primer torneo porque su origen ya fue un experimento de especialización matemática y selección de motores.

Objetivo:

> Encontrar una base de tres operaciones que maximice utilidad matemática/topológica para WISA bajo el contrato de ISyCoLang.

No diseñar las tres ops ganadoras a mano.

### Fases WISA

1. congelar corpus matemático;
2. congelar atomicity contract;
3. definir catálogo inicial de ops;
4. enumerar ternas;
5. sintetizar programas;
6. ejecutar con engine de referencia;
7. medir cobertura/costo;
8. seleccionar Pareto frontier;
9. reejecutar finalistas en Python/Rust/Zig;
10. producir evidence pack;
11. congelar `WISA_BASIS_3_V0` si sobrevive.

Después:

> **a chingar a su madre; siguiente dominio. :p**

## 17. Milestones

### M0 — Core skeleton

- estado;
- memoria;
- tres slots;
- dispatch;
- halt;
- trace;
- deterministic fixture.

**Gate:** dos packs distintos corren sobre el mismo core sin modificarlo.

### M1 — Operation contract

- schema de op;
- atomicity validator;
- cost model;
- versioning.

**Gate:** una op inválida tipo hidden-VM es rechazada.

### M2 — 3OPS Arena

- enumeración de ternas;
- runner;
- corpus mínimo;
- scoreboard.

**Gate:** 12 ops -> 220 packs reproducibles.

### M3 — Synthesis V0

- búsqueda de programas acotados;
- shortest witness;
- negative cases.

**Gate:** al menos dos packs muestran cobertura/costo diferentes bajo el mismo corpus.

### M4 — TRACE_MATH bridge

- trace normalization;
- composed behavior;
- derivation records.

**Gate:** una operación derivada se reconstruye a partir de una composición previamente verificada.

### M5 — WISA tournament

- corpus WISA;
- finalists;
- Pareto frontier;
- evidence pack.

**Gate:** `WISA_BASIS_3_V0` seleccionado por métrica, no manualmente.

### M6 — Engine race

- Python;
- Rust;
- Zig.

**Gate:** mismos programas/semántica, resultados equivalentes, benchmarks separados.

### M7 — Second domain

Repetir sin cambiar core.

**Gate:** demostrar que ISyCoLang no era una máquina WISA disfrazada.

### M8 — Universality research

Sólo aquí estudiar formalmente packs Turing-complete y reducciones `3 -> 2 -> 1`.
